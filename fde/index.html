왜 FDE를 하려는가

영업·CS에서 고객 요구를 듣는 일로 시작해, 개발을 통해 제품을 개선하는 일까지 해 왔습니다. 고객의 문제를 이해하고 관계자를 조율하며 PoC를 실제 도입까지 이어 온 경험이 FDE 업무와 잘 맞는다고 생각합니다.

CS → 제품 개선

크리니티에서 고객사 13개 CS 채널을 맡아 운영 이슈의 원인을 찾았습니다. 단순히 티켓을 처리하는 데 그치지 않고, 반복되는 문제를 기능과 구조를 고치는 일로 이어 갔습니다.

  • 고객사별 요구사항·버그·예외 케이스 반영
  • 레거시 검색·외부 API 등 구조적 병목 개선

이해관계자 조율 (영업 경력)

한국학술정보 솔루션영업과 다다무역 해외영업으로 일하며 약 4년간 B2B 고객·생산처·유관부서 사이에서 요구사항을 정리하고 일정을 맞췄습니다.

  • 공공·대학·연구기관 고객 문의/요구사항 대응
  • 개발·디자인·CS와 협업해 서비스 개선 진행

PoC → NIA 도입

Spring AI로 공공 메일 AI 기능 PoC를 직접 설계하고 구현했습니다. G-Cloud 공공 클라우드 메일 AI 기능 PoC로 채택된 뒤 한국지능정보사회진흥원(NIA) 베타 운영 환경에 도입됐습니다.

  • RestTemplate 단일 프롬프트 한계를 ChatClient 구조로 전환
  • RAG·에이전트·Langfuse 확장 가능 구조 설계

관측성 · 운영 구조 개선

KISTI 프라이빗 클라우드에 ELK/Fleet/APM을 구축해 VM별 root 접속 로그를 확인하던 방식에서 Kibana로 한곳에서 조회하는 방식으로 바꿨습니다. 장애·CS 대응 시간도 기존의 약 30% 수준으로 줄였습니다.

  • Admin/Readonly 권한 분리로 로그 접근 보안 개선
  • APM Slow Query로 SQL 조건 개선
